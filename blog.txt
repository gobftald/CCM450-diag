1 defmt put the majority of the weight/length of the printing/debugging text to the host side
2 defmt filtering can even eliminate (println, trace, debug, info, warn, error) from the defmt-ed code
3 core::fmt which is the final fragments of code after panic (hence asserts, todo, unreachable, unwrap)
can also be eliminated via 'build-std-features = ["panic_immediate_abort"]', which prevents core::panic
to call panic_fmt which cannot trigger core::fmt code fragments and its static strings (panic messages,
and file or line information strings) then even does not call panic_handler
it is relevant even in 'demt version' of code, since defmt::panic and its relatives finally call core::panic
and furthermore there can be other external/imported crates in the program which use 'core library' where we
cannot disable functions or the compiler standard 'checks' (e.g. array boundary checks) to call core::panic
4 so even in defmt/printing/debugging/monitoring development phase we can fully eliminate core::fmt overhead
and totally control the amount of code caused by defmt
5 location info of panic can be see both normal and backtrace build when defmt and "panic_immediate_abort"
is off, this is when we can get and display core::panic::PanicInfo


6 in the production code we want only to simply switch off defmt in order to switch everything which relates
to printing and formatting
7 but defmt filtering needs defmt itself, so we make custom (println, trace, debug, info, warn, error) macros,

To implement the InterruptExecutor from the esp-rtos crate, you must manually bind a software interrupt to a handler that calls on_interrupt(). This allows the executor to preempt the standard thread-mode tasks. 
Implementation Example
The following example demonstrates how to set up a software interrupt to drive the InterruptExecutor using a static instance. 
rust
use esp_rtos::embassy::InterruptExecutor;
use esp_hal::interrupt::software::SoftwareInterruptControl;
use esp_hal::interrupt::Priority;
use static_cell::StaticCell;

// 1. Define a static executor to ensure it lives for the duration of the program
static INT_EXECUTOR: StaticCell<InterruptExecutor> = StaticCell::new();

#[esp_rtos::main]
async fn main(spawner: embassy_executor::Spawner) {
    let peripherals = esp_hal::peripherals::Peripherals::take();
    
    // 2. Access software interrupts (SWI)
    let sw_ints = SoftwareInterruptControl::new(peripherals.SW_INTERRUPT);
    let mut swi0 = sw_ints.software_interrupt0;

    // 3. Bind the interrupt handler to the executor's polling function
    // The handler MUST call on_interrupt() to process pending async tasks
    swi0.set_interrupt_handler(swi0_handler);

    // 4. Initialize and start the executor at a specific priority
    // Priority must be set BEFORE calling start()
    let executor = INT_EXECUTOR.init(InterruptExecutor::new(swi0));
    let int_spawner = executor.start(Priority::Priority1);

    // 5. Spawn a task onto the high-priority interrupt executor
    int_spawner.spawn(high_priority_task()).unwrap();

    loop {
        embassy_time::Timer::after_secs(1).await;
    }
}

// The interrupt handler that polls the executor
#[esp_hal::handler(priority = Priority::Priority1)]
fn swi0_handler() {
    unsafe {
        // Access the static executor to trigger polling
        INT_EXECUTOR.uninit_mut().on_interrupt();
    }
}

#[embassy_executor::task]
async fn high_priority_task() {
    loop {
        // This task runs in interrupt mode and can preempt thread-mode tasks
        esp_println::println!("High priority task running!");
        embassy_time::Timer::after_millis(500).await;
    }
}
Use code with caution.

Critical Implementation Details
Interrupt Handler: You must use the #[esp_hal::handler] attribute to mark your function as an interrupt service routine.
Priority Management: The priority defined in the handler attribute should match the priority passed to the .start() method.
on_interrupt(): This method is the engine of the executor. It must be called from the handler to ensure that whenever a task is ready (woken up), the CPU executes it immediately.
Task Spawning: Use the SendSpawner returned by executor.start() to queue tasks from other threads or executors.

To use the InterruptExecutor with a peripheral like UART, you bind the UART interrupt directly to the executor's interrupt handler. Instead of manually "triggering" it, the hardware does the work: when data arrives, the UART interrupt fires, and the executor automatically polls your async tasks.
UART Interrupt Executor Setup
In this pattern, the InterruptExecutor runs "on top" of the UART interrupt.
rust
use esp_hal::interrupt::{self, Priority};
use esp_hal::peripherals::UART0;
use esp_hal::uart::Uart;
use esp_rtos::embassy::InterruptExecutor;
use static_cell::StaticCell;

static INT_EXECUTOR: StaticCell<InterruptExecutor> = StaticCell::new();

#[esp_rtos::main]
async fn main(_spawner: embassy_executor::Spawner) {
    let peripherals = esp_hal::peripherals::Peripherals::take();
    let mut uart0 = Uart::new(peripherals.UART0, peripherals.GPIO1, peripherals.GPIO2).unwrap();

    // 1. Setup the UART interrupt handler
    uart0.set_interrupt_handler(uart0_interrupt_handler);

    // 2. Initialize the InterruptExecutor using the UART peripheral's interrupt
    // This links the executor's wakeups to the UART0 hardware interrupt
    let executor = INT_EXECUTOR.init(InterruptExecutor::new(peripherals.UART0));
    let int_spawner = executor.start(Priority::Priority1);

    // 3. Spawn a task that handles the UART data asynchronously
    int_spawner.spawn(uart_reader_task(uart0)).unwrap();

    loop {
        embassy_time::Timer::after_secs(1).await;
    }
}

// 4. The hardware interrupt handler for UART0
#[esp_hal::handler(priority = Priority::Priority1)]
fn uart0_interrupt_handler() {
    unsafe {
        // This polls the executor whenever the UART hardware triggers an interrupt
        // (e.g., RX buffer full, error, or end of transmission)
        INT_EXECUTOR.uninit_mut().on_interrupt();
    }
}

#[embassy_executor::task]
async fn uart_reader_task(mut uart: Uart<'static, UART0>) {
    let mut buffer = [0u8; 64];
    loop {
        // This 'read' is async and will yield. 
        // When data arrives, the UART interrupt fires, calling uart0_interrupt_handler,
        // which calls on_interrupt(), waking this task up.
        if let Ok(len) = uart.read_async(&mut buffer).await {
            esp_println::println!("Received: {:?}", &buffer[..len]);
        }
    }
}
Use code with caution.

Why this works
Hardware Trigger: The UART hardware raises an interrupt signal when specific conditions are met (like RX_FIFO_FULL).
Executor Polling: The uart0_interrupt_handler catches that signal and tells the InterruptExecutor to check its tasks.
Zero Latency: Because the executor is running inside the interrupt, the uart_reader_task resumes almost instantly after the hardware signal, bypassing the standard thread-mode scheduler.
Important Note: When using InterruptExecutor with a specific peripheral, that peripheral's interrupt cannot be used for other purposes by the thread-mode executor simultaneously.
